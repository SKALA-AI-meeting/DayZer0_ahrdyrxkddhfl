# Day Zer0 — AI 동료 협업 시뮬레이션 채용 평가 (MVP)

지원자가 AI 동료(이도현)·AI 팀장(한서윤)·AI 어시스턴트와 함께 2시간짜리 가상 리모트 업무를 하고, 기업은 그 과정에서 드러난 **협업 행동·인성·AI 활용**을 **점수 없이 근거 원문과 시각으로** 받습니다. 최종 판단은 채용 담당자가 합니다.

- 기획 기준: 팀 공통 PRD(Slack, 2026-10-20 SSoT). **기능(F-xx)·시나리오(6장)는 그대로** 구현했고, 부록(기술 설계)만 바꿨습니다(아래 "레퍼런스와 다른 점").
- 상태: 화면·API·에이전트·MCP 2개·벡터 검색·리포트까지 처음부터 끝까지 동작. 시나리오 팩 2개(공통 PRD + 기업 맞춤 예시). 테스트 75개, 실제 LLM 평가셋 3종 포함.

## 1. 실행

필요: Python 3.11, [uv](https://docs.astral.sh/uv/), Node.js 20+

```bash
uv sync --python 3.11 --group dev          # 파이썬 의존성(버전은 uv.lock에 고정)
cp .env.example .env                       # OPENAI_API_KEY, AUTH_SECRET 입력 (LangSmith는 선택)
cd web && npm ci && cd ..                  # 화면 의존성
```

```bash
# 터미널 1: 백엔드(gateway + 에이전트). MCP 서버 2개는 에이전트가 stdio로 자동 실행
uv run uvicorn app.api:app --port 8000
# 터미널 2: 화면
cd web && npm run dev                      # http://localhost:3000
```

**써 보기**: 첫 화면 → 채용 담당자 → 회사 계정 만들기 → 지원자 초대 → 링크 복사 → 새 탭에서 링크 열기(지원자는 가입 없이 링크로 입장) → 안내·동의 → 가상 오피스 → 제출 → 디브리핑. 관리자 목록에서 "리포트 준비됨"이 되면 리포트 보기.

| 명령 | 하는 일 |
|---|---|
| `uv run python -m app.cli` | 화면 없이 2시간 세션을 가짜 시계로 몇 분 만에 끝까지 돌리고 리포트 출력 |
| `uv run python -m app.cli eval/scripts/demo_pixel.toml pixel` | 같은 엔진으로 다른 회사(픽셀게임즈) 시나리오 실행 |
| `uv run --group dev python -m pytest -q` | 테스트 75개 (LLM·네트워크 없이) |
| `uv run python eval/run_eval.py 3` | 관찰 판별 평가(A/B 비교, 3회 반복) |
| `uv run python eval/run_verify_eval.py 3` | 발화 검증 평가(필수 내용·출처·레드팀) |
| `uv run python eval/run_rag_eval.py` | 검색 평가(keyword vs vector, 실제 임베딩) |

시연 배속: `config.toml`의 `[session] time_scale = 12` → 2시간 세션이 10분.

## 2. 구조

```
브라우저 ── web (Next.js, 화면만) ──/api 프록시──▶ gateway (FastAPI, app/api.py)
                                                   │  인증(관리자 토큰 · 지원자 초대 토큰)
                                                   ▼
                                       agent (LangGraph, 같은 프로세스)
                         ┌─────────────────┬────────────────────┬────────────────────┐
                    세션 Graph          발화 Graph            문서 등록 Graph      관찰·리포트
                 (장면·분업·답장)   (생성→검증→재생성/대체)   (interrupt 승인)    (하이브리드 판별)
                         └────────┬────────┴──────────┬─────────┘
                       MCP stdio  ▼                    ▼  MCP stdio
              business-mcp (직접 구축)           rag-mcp (직접 구축)
              세션·태스크·공유 문서·관찰 기록      회사 문서 검색·원문 Resource·등록
                         └──────────────┬─────────────┘

```

| 폴더 | 내용 |
|---|---|
| `app/` | gateway, 세션 시계, Graph 3개, 발화 검증, 관찰·리포트, 인증, 저장소 |
| `mcp_servers/` | **직접 만든 MCP 서버 2개** (business, rag) |
| `scenario/` | 시나리오 팩. `moarun/` = PRD 6장 공통 시나리오 그대로(기본), `pixel/` = 기업 맞춤 시나리오 예시(게임 회사) |

### 시나리오 팩: 회사를 갈아끼우기 (기업 맞춤 시나리오, PRD 확장)

에이전트 코드는 그대로 두고 **데이터(시나리오 팩)만 바꾸면 전혀 다른 회사의 시뮬레이션**이 됩니다. 관리자가 초대를 만들 때 채용 건의 시나리오를 고르고, 같은 채용 건의 지원자는 모두 같은 팩을 씁니다(PRD 5.5 "조건은 모두에게 같다").

| | 모아런 (기본, 공통 PRD) | 픽셀게임즈 (확장 예시) |
|---|---|---|
| 회사·서비스 | 루프랩 · 러닝 모임 앱 | 픽셀게임즈 · 모바일 RPG |
| 과제 | 첫 모임 재참여율 22% 개선 | 신규 유저 7일 잔존율 18% 개선 |
| 등장인물 | 한서윤 팀장 · 이도현 | 강민재 팀장 · 윤하늘 |
| 01:10 대상 변경 | 3개월 넘게 안 나온 사용자 | 30일 넘게 미접속한 복귀 유저 |
| 01:30 동료 실수 | 유료 멤버십 (올해 유료 기능 금지) | 확률형 전설 상자 (확률형 보상 금지) |

팩마다 이벤트 id·시점·관찰 요소가 같아서 엔진·검증·관찰 코드가 그대로 동작합니다. rag-mcp는 코드가 채우는 `scenario` 인자로 그 회사 문서만 검색하고, 벡터 색인도 팩별로 나뉩니다. 프롬프트는 `{company}`, `{coworker_name}` 같은 자리에 팩 값을 넣습니다.

## 4. AI Agent 설계: Graph 3개

**① 세션 Graph** (`app/graph.py`) — 입력 하나(정해진 시각이 된 장면 또는 지원자 메시지)를 처리

```
START ─┬─ 이벤트 장면 + 아직 분업 중 ─→ finalize_split ─→ run_scene ─→ END
       ├─ 장면 ─────────────────────→ run_scene ─→ END
       ├─ 분업 중 + 동료 1:1 ─→ check_agreement ─┬─ 분업 얘기 아님 → reply
       │                                        ├─ 합의 / 조정 3회 도달 → apply_assignment
       │                                        └─ 미합의 → counter_proposal  (다음 메시지에서 다시 판단: 반복, F-21)
       └─ 그 외 ─→ reply ─→ END
```

**② 발화 Graph** (`app/speak_graph.py`) — 동료·팀장·어시스턴트가 말 한 마디를 만드는 공통 Graph

```
START → llm ─┬─ 도구 호출(한도 안) → tools → llm          ← 도구 순환 (Agent Loop)
             └─ 답 완성 → verify ─┬─ 통과 → done
                                  ├─ 실패 + 재시도 가능 → feedback → llm   ← 검증 순환
                                  └─ 실패 + 한도 초과 → fallback (사실을 지어내지 않는 대체 문장)
```

**③ 문서 등록 Graph** (`app/doc_graph.py`, F-06) — 사람 승인 후 같은 지점에서 재개

```
START → prepare(형식 검사·개인정보 마스킹) → approval: interrupt() ← 멈추고 thread_id별 상태 저장
        → 관리자 승인 → Command(resume)로 재개 → register(rag-mcp 변경 도구, 승인 토큰 필수)
        → 관리자 거절 → reject
```

세션 진행 시각은 **세션 시계**(`app/clock.py`)가 정합니다. 화면이 서버에 묻는 동안의 시간만 누적해, 창을 닫으면 멈추고 다시 들어오면 이어집니다(F-19). 장면은 DB의 PRIMARY KEY로 한 번만 실행됩니다(F-23).

## 5. MCP: 직접 구축한 서버 2개 (stdio)

| 서버 | 조회 도구 | 변경 도구 (destructiveHint) | Resource |
|---|---|---|---|
| **business-mcp** | `get_session_status`, `list_tasks`, `read_shared_plan`(동료·팀장이 기획안 읽기), `list_observations` | `assign_tasks`, `update_task_status`, `save_observation` | — |
| **rag-mcp** | `list_company_docs`, `search_company_docs`(벡터 검색, 실패 시 키워드), `read_company_doc` | `register_company_doc` (승인 토큰 없으면 거부) | `docs://{session_id}/{doc_id}` 원문, `scenario://brief` |

- **모델이 고르는 도구**: 동료·팀장·어시스턴트는 문서 검색·읽기 도구를, 동료·팀장은 `read_shared_plan`을 스스로 골라 호출합니다.
- **모델이 속일 수 없는 인자**: 세션 시각·기업·세션 id는 모델이 아니라 코드가 넣습니다. 그래서 01:05 전에 인터뷰 요약을 미리 읽을 수 없습니다(F-15). Resource는 시각 인자가 없으므로 MCP 서버가 DB에서 세션 시각을 직접 읽어 판단합니다.
- **벡터 검색**(`app/embedding.py`): 문서 → 문단 청크 → `text-embedding-3-small` 임베딩 → SQLite 색인(모델 이름·차원 기록) → 질문 임베딩과 코사인 유사도. 내용 해시가 같으면 다시 임베딩하지 않고, 기업이 등록·교체한 문서는 다음 검색 때 자동 색인. 임베딩 호출이 실패하면 키워드 검색으로 대신 찾고 결과에 `via`로 방식을 밝힙니다.
- **오류 처리**: 없는 세션·문서, 잘못된 값, 공개 전 문서, 승인 없는 등록은 오류로 돌려주고, 코드가 부르는 변경 도구는 오류 응답을 예외로 올려(`check_result`) 실패를 성공으로 착각하지 않습니다.

## 7. AI를 어떻게 검증했나

**원칙: AI가 만든 결과를 그대로 내보내지 않고, 코드가 원문·기록과 대조해 통과한 것만 쓴다.**

| 검증 | AI가 저지르는 실수 | 코드가 확인하는 것 | 실패하면 |
|---|---|---|---|
| 판정 발언 (F-24) | 점수·합격·연출될 상황을 말함 | 금지 표현 | 재생성 → 안내문 |
| 필수 내용 (F-23) | 이벤트 대사에서 핵심 사실 누락 | `events.toml` must_include | 재생성 → 정해진 대사 |
| 출처 (F-22) | 읽지 않은 문서를 근거로 댐 | 답에 나온 문서 제목이 이번에 도구로 실제 읽은 문서인지 | 재생성 |
| 말만 하고 실행 안 함 | "확인해 볼게요"라 하고 도구를 안 부름 | 약속 표현 + 이번 답의 도구 호출 0회 | "지금 확인해 답하라" 재생성 |
| 찾아보지도 않고 포기 | "제공할 수 없습니다"라며 검색을 안 함 | 포기 표현 + 이번 답의 도구 호출 0회 | "먼저 검색해 보고 답하라" 재생성 |
| 검토 요청 무시 | "봐주세요"에 문서를 안 읽고 답함 | `read_shared_plan` 실제 호출 여부 | 재생성 |
| 관찰 인용 | 리포트 근거로 대화에 없는 문장을 지어냄 | 인용이 원문에 있는지·허용 범위 안인지 | 근거에서 제외 |

실제 사례(개발 중 로그): 어시스턴트가 "지표 현황" 내용을 "사용자 인터뷰 요약에 따르면"이라고 답함 → 출처 검증이 잡음 → 재생성 시 `read_company_doc("interviews")`로 실제 문서를 읽고 정확히 답함.

**평가 결과** (실제 gpt-4o-mini, `eval/results.md`)

| 평가 | 결과 |
|---|---|
| 관찰 판별 체크 정확도 (3사례 × 14항목) | 41/42 |
| 같은 대화 3회 반복 일관성 | 42/42 |
| 요소 정확도: A(규칙만) vs **B(하이브리드)** | 7/12 vs **12/12** (키워드 없이 바꿔 말한 사례 A 0/4 → B 4/4) |
| 장면 필수 내용 (7장면 × 3회) | 21/21 |
| 출처·실행·검토 요청 질문 | 6/6 |
| 판정 발언·미공개 정보 레드팀 | 누출 0/6 |
| 2시간 데모 세션 | LLM 26회 오류 0, 발화 검증 17회 중 1회 필수 내용 누락을 잡아 재생성 |
| 검색 (바꿔 말한 질문 10개) | 정답 문서 1위: keyword 8/10 → **vector 9/10**, 상위 3개 안: 9/10 → **10/10** |

**관찰 판별 방식 (하이브리드 B)**: 시각·유사도처럼 표현과 무관한 것은 규칙으로 확정, 키워드는 관련 메시지 "후보"만 찾고, 의미 판단(해결책 제안·대안 제시 등)은 LLM 체크리스트(예/아니오 + 원문 인용, temperature 0, 캐시). 집계·인용 검증은 코드. 리포트에는 점수·개수 없이 행동과 원문만 나갑니다. 한계: 애매한 표현("나눈 걸 다시 맞춰 볼게요")은 놓칠 수 있습니다(평가셋 1건).

**지원자의 AI 검증 행동도 관찰**: AI 활용 요소에서 "요청에 목표·조건을 담았는가", "결과를 회사 문서와 대조했는가"를 봅니다. 후자는 어시스턴트가 근거로 든 문서를 지원자가 **그 답 이후에 직접 열어 봤는지** 열람 기록으로 확정합니다. 어시스턴트 답을 기획안에 그대로 썼는지/고쳐 썼는지는 유사도로 구분합니다(F-31).

## 8. 레퍼런스(PRD 부록·교안)와 다른 점과 이유

| 레퍼런스 | 이 MVP | 이유 |
|---|---|---|
| PostgreSQL + pgvector | SQLite | 설치 없이 바로 실행·테스트(테스트마다 임시 DB). 저장소 함수(`app/store.py`)만 바꾸면 이전 가능 |
| MCP Streamable HTTP (별도 컨테이너) | MCP stdio (에이전트가 자식 프로세스로 실행) | 로컬 MVP에서 포트·컨테이너 없이 동작. 서버 코드는 `mcp.run(transport=...)`만 바꾸면 HTTP로 전환 |
| business-mcp가 gateway 내부 API 경유 | 같은 SQLite 파일을 직접 읽음 | 프로세스 하나 줄여 단순화. 변경은 모두 MCP 도구를 거침 |
| 미리 색인한 Vector DB (BGE-M3 + pgvector) | 미리 색인한 임베딩(`text-embedding-3-small`) + SQLite + 코사인 유사도, 실패 시 키워드 | 팀 키로 쓸 수 있고 새 라이브러리·로컬 모델 다운로드가 필요 없음. 문서 수가 적어 별도 벡터 DB 없이 충분. 저장소만 pgvector로 바꾸면 이전 가능 |
| 202 + SSE 진행 이벤트 | 화면이 2초마다 조회(poll) + 진행 이벤트 필드 | 장면을 정시에 실행하는 시계와 같은 조회로 처리해 스케줄러 불필요 |
| RabbitMQ 리포트 큐 | 백그라운드 작업 + 2회 재시도 + 재시작 시 재생성 | MVP 범위. 같은 재시도·실패 처리 규칙 유지 |
| 체크포인터 Postgres | 문서 승인 대기는 메모리 체크포인터 | 서버 재시작 시 대기 중 승인 요청이 사라지는 한계(세션·리포트는 SQLite라 유지) |
| 관찰 지표는 규칙, LLM은 근거 정리만 (부록 A.4) | 의미 판단만 LLM 체크리스트 | 규칙만으로는 바꿔 말한 행동을 0/4 놓침(§7 평가). 재현성은 temperature 0 + 캐시 + 반복 평가로 보완 |

**품질 특성(ISO/IEC 25010) 대응**: 신뢰성 — LLM 재시도·대체 대사·리포트 재생성·장면 중복 방지·임베딩 실패 시 키워드 검색 / 보안 — 비밀번호 해시, 서명 토큰, 기업별 데이터 분리, 승인 토큰, 개인정보 마스킹, `.env` 비공개 / 유지보수성 — 시나리오·숫자·프롬프트를 코드 밖 파일로 분리 / 시험성 — 테스트 75개, 평가셋 3종. 이식성 — 시나리오 팩 교체로 다른 회사 적용.

## 9. PRD 구현 메모 (PRD가 정하지 않은 빈칸을 채운 것)

PRD에 적힌 동작은 바꾸지 않았습니다. 정해지지 않은 부분만 아래처럼 채웠습니다.

| 빈칸 | 처리 |
|---|---|
| 분업을 바꾸면 이벤트 대사가 기본 분업과 안 맞을 수 있음 (F-21 vs F-23) | 둘 다 그대로. 상황이 성립하지 않으면 리포트에 "관찰 없음"(F-33). 01:30 공유 때 지원자가 맡은 파트는 덮어쓰지 않음 |
| 30분까지 분업 조정이 안 끝남 | 첫 이벤트 직전에 지금 안으로 확정(F-21 "마지막 안으로 진행"과 같은 방식) |
| 동료·팀장이 공유 문서를 읽을 수 있는가 | 읽기만 가능(편집은 지원자). 어시스턴트는 읽지 않음(요청에 맥락을 담는지 관찰하기 위해) |
| 동료 작업이 01:30 전에는 보이지 않음 | 보드 카드가 분업 확정 시 "진행 중", 공유 시 "완료". 공유 시각은 비공개 |
| 팀장이 1:1 대화를 보는가 | 팀 채널·알림만 봄 |
| 회사 문서 본문 수치·인터뷰 발언 | PRD에 적힌 사실(22%, 3만 명, 8명, 유료 기능 없음 등)은 그대로, 나머지는 이 MVP에서 채운 가상 값 |
| F-31 "그대로 씀/고쳐 씀" 기준 | 유사도 0.9 이상 그대로 씀, 0.4 이상 고쳐 씀 (`config.toml`) |
| F-06 문서 등록 승인 | PRD상 P1이지만 과제 Harness(변경 도구 승인 후 재개) 때문에 구현 |
| 지원자 입장 | 가입 없이 초대 링크(F-02, F-10). MVP는 이메일을 보내지 않으므로 관리자가 링크를 복사해 전달 |
